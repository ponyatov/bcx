# Принцип работы стековой модели вычислений

Стековая модель вычислений — это способ организации вычислений, при котором операнды и результаты операций размещаются в специальной структуре данных — **стеке**, работающем по принципу LIFO (Last In, First Out, «последним пришёл — первым вышел»).

В отличие от регистровых архитектур, и архитектур память-память, где в коде команд явно указывается, где брать операнды и куда записывать результат, в стековой модели местонахождение операндов неявно определяется самим стеком:
- **операция всегда берёт свои входные данные с вершины стека**
- и возвращает результат туда же, на вершину стека.

> Ключевое свойство стековой модели: операнды не кодируются в команде

Пример вычисления `3 + 4`:
```
PUSH 3      ; 2 байта: опкод и операнд; стек: [3]
PUSH 4      ; 2 байта;                  стек: [3, 4]
ADD         ; 1 байт: опкод;            стек: [7]
            ; ∑ 5
```

Сравните с регистровой архитектурой, где потребовалось бы что-то вроде:
```
MOV R1, 3        ; 2 байта: 4 бита опкод, 
                 ;          4 бита индекс регистра,
                 ;          1 байт операнд
MOV R2, 4        ; 2 байта
ADD R3, R1, R2   ; 2 байта: 4 бита опкод,
                 ;          12 бит регистры-операнды
                 ; ∑ 6
```

Подходящий реальный процессор — ARMv7. Приведённые регистровые команды и их длины в реальном ARM имеют **значительно б*о*льшую длину**: все инструкции фиксированной длины **4 байта**, поэтому реальный машинный код будет состоять из 3 инструкций по 4 байта:
```
Адрес   Байты (hex) ∑ 12    Инструкция

0000:   03 10 A0 E3         MOV R1, #3
0004:   04 20 A0 E3         MOV R2, #4
0008:   02 30 81 E0         ADD R3, R1, R2
```

## Постфиксная (обратная польская) запись

Для стековой модели естественной является **постфиксная запись** выражений, где оператор ставится после операндов:

|Инфиксная запись|Постфиксная запись|
|---|---|
|`3 + 4`|`3 4 +`|
|`(3 + 4) * 5`|`3 4 + 5 *`|
|`a * (b + c)`|`a b c + *`|

Постфиксная запись не требует скобок: порядок операций однозначно определяется порядком следования констант и операторов. Это делает её идеальной для однопроходной компиляции в стековый байткод.

В языке Форт принято указывать **стековый эффект** как минимум для определений новых слов, а также некоторых фрагментов кода — формальная запись того, как слово (или фрагмент кода) изменяет состояние стека данных. Он записывается в виде скобочного комментария:

```
: DUP  ( n -- n n )  ... ;
: +    ( n1 n2 -- n1+n2 ) ... ;
: SWAP ( a b -- b a )  ... ;
```

- вершина стека справа
- разделитель `--` указывает состояние до/после выполнения слова
- для промежуточного кода иногда указывают только текущее состояние стека
- `( -- )` — слово/команда без операндов, не берёт и не оставляет ничего
- `( x -- )` — слово снимает элемент и ничего не возвращает
- `( -- x )` — слово кладёт элемент
- `*` в некоторых нотациях — «и остальное»: `( n * -- n * )`
- `type ( addr:*char n:int -- )` можно уточнить типы операндов

## Конкатенативное программирование

Конкатенативное программирование — это парадигма, в которой программа строится **путём последовательного соединения (конкатенации) фрагментов кода**, а не путём применения функций к аргументам. Каждый фрагмент кода имеет фиксированный «интерфейс» со стеком, и соединение двух фрагментов корректно, если выходное состояние стека первого фрагмента совместимо со входным стеком второго.

Термин ввёл **Манфред фон Тун** (Manfred von Thun) в 1989 году для описания языка Форт и близких ему языков (`Joy`, `Factor`, `Cat`). Ключевая идея: **композиция — это просто запись подряд**, без явных параметров, скобок или операторов применения.

- В лямбда-исчислении и функциональном программировании функция — это отображение значений в значения: `f : A → B`.
- В конкатенативном программировании слово — это отображение **состояния стека** в состояние того же стека: `f : Stack → Stack`
- Тогда композиция `f` и `g` — это просто `f g`: сначала выполняется `f`, затем `g`. Никакого оператора композиции не нужно — **сама запись подряд и есть композиция**.

Пример: вычисление `(a + b) * c` в разных парадигмах.

|Парадигма|Запись|
|---|---|
|Инфиксная|`(a + b) * c`|
|Функциональная|`(* c (+ a b))` или `(* (c) (+ (a) (b)))`|
|Конкатенативная|`a b + c *`|

В конкатенативном языке «тип» слова описывается его **стековым эффектом** — парой «что снимается / что кладётся»:
```
+      ( n1:int n2:int -- n3:int )
       ( a:addr n:uint -- n3:addr )
DUP    ( n:any -- n n )
SWAP   ( a b -- b a )
```

Это аналог сигнатуры `f : A × B → C` в функциональном программировании, но записанный в терминах стека.

> Композиция `f g` корректна тогда и только тогда, когда выход `f` совместим со входом `g`.

### Недостатки

1. **Читаемость для новичков**: постфиксная запись непривычна; порядок операндов задом наперёд по сравнению с инфиксной.
2. **Отладка стека**: при ошибке легко испортить стек, и источник ошибки не очевиден.
3. **Избыточность перестановок**: для сложных выражений может потребоваться много `SWAP`/`ROT`/`DUP`.
4. **Неявные потоки данных**: сложно проследить, откуда пришло значение, без трассировки.

### Стек возвратов и проблема вложенности

Разделение стека данных и стека возвратов — не просто удобство, а **семантическая необходимость** при конкатенативном подходе. Если бы оба стека были одним, слово `>R` (пересылка на стек возвратов) смешивало бы управляющий и вычислительный контексты, делая композицию небезопасной: слово, меняющее глубину или содержимое стека возвратов, нельзя свободно комбинировать.

## Проблема дна стека и переполнения

В реальных ВМ стек конечен. Возникают две классические проблемы:

1. **Underflow** — попытка снять элемент с пустого стека. В [[bcx]] это должно приводить к детерминированному исключению, а не к чтению мусора из памяти.
    
2. **Overflow** — переполнение стека. Для embedded-систем важно резервировать фиксированный регион памяти под стек

Желательно проверять код на исключения стека статически -- на этапе компиляции, а не в рантайме (предсказуемость важнее гибкости). К сожалению реализация статической верификации кода выходит далеко за рамки книги, и можно только порекомендовать писать побольше разнообразных тестов чтобы ловить такие ошибки в динамике, но не в проде.
