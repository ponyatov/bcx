# DAP-сервер и жизненный цикл отладочной сессии

Расширение работает с ВМ в отладочной сборке, которая предоставляет отладочный интерфейс по протоколу **Debug Adapter Protocol (DAP)**:
[dap://127.0.0.1:4711](dap://127.0.0.1:4711)

Всё, что нужно IDE (выполнение кода из редактора, командная консоль, пошаговое исполнение, просмотр стеков, памяти и словаря, дизассемблер, логирование,..) предоставляется виртуальной машиной в динамике.

DAP-сервер (ВМ) общается с клиентом (VSCode) через локальное сетевое соединение JSON-сообщениями с `Content-Length`-фреймингом (как и в LSP).

## Жизненный цикл сессии

```
client                              server (bcx)
  |── initialize ───────────────────>|
  |<────────────────── initialize resp (capabilities)
  |── launch {program} ─────────────>|  поднять ВМ, загрузить байткод
  |── setBreakpoints ───────────────>|  заполнить breakpoint[]
  |── configurationDone ────────────>|
  |<────────────────── stopped (entry)   [если stopAtEntry]
  |── continue ─────────────────────>|
  |<────────────────── stopped (breakpoint)
  |── stackTrace / scopes / variables
  |── evaluate {expr} ──────────────>|  REPL: компиляция + исполнение
  |<────────────────── evaluate resp
  |── disconnect ───────────────────>|  завершить ВМ
```

- `launch` vs `attach`:
	- `launch` сам поднимает новый процесс ВМ (см. [[launch.json#bcx]])
	- `attach` цепляется к уже работающей ВМ
- `initialize` возвращает **capabilities**:
	- какие отладочные запросы поддерживаются
	- это ограничивающий контракт: клиент не должен слать запросы вне заявленного набора.
- `configurationDone` — точка синхронизации
	- код загружен
	- ВМ инициализирована, и стоит на входной точке кода
	- точки останова уже расставлены
